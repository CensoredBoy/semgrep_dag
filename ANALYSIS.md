# Анализ правил Semgrep для Airflow DAG файлов

## Обзор

Этот документ содержит анализ того, какие правила Semgrep нужно **усилить** (сделать строже) и какие **ослабить** (исключить или понизить severity) специально для DAG файлов Apache Airflow.

---

## 🔴 ПРАВИЛА, КОТОРЫЕ НУЖНО УСИЛИТЬ

### 1. **Remote Code Execution (RCE) - КРИТИЧНО**

#### Текущее состояние
- ✅ Есть кастомные правила для `eval()`, `exec()`, `pickle.loads()` в `python_callable`
- ✅ Есть правила для `os.system()` и `subprocess` с `shell=True`

#### Что нужно усилить:

**1.1. Запрет eval/exec в любом контексте DAG**
- **Текущее правило:** Проверяет только в `python_callable`
- **Усиление:** Запретить `eval()` и `exec()` **везде** в DAG файлах, не только в `python_callable`
- **Причина:** Даже если `eval()` не в `python_callable`, он все равно опасен в DAG

**1.2. subprocess без shell=True тоже может быть опасным**
- **Текущее правило:** Проверяет только `shell=True`
- **Усиление:** Добавить проверку на использование `subprocess` с данными из `dag_run.conf`/`params`/XCom даже без `shell=True`
- **Причина:** Если команда строится из внешних данных, это все равно инъекция

**1.3. Запрет pickle.loads/marshal.loads везде**
- **Текущее правило:** Проверяет только в `python_callable`
- **Усиление:** Запретить везде в DAG файлах
- **Причина:** Pickle небезопасен при десериализации недоверенных данных

**Рекомендация:** Создать правило `airflow-rce-strict.yml` с более строгими проверками.

---

### 2. **SQL-инъекции - КРИТИЧНО**

#### Текущее состояние
- ✅ Есть правила для конкатенации строк в SQL операторах
- ✅ Есть правила для f-строк в SQL

#### Что нужно усилить:

**2.1. Запрет любой конкатенации в SQL операторах**
- **Текущее правило:** Проверяет f-строки и `+`, но может пропустить `.format()`, `%` форматирование
- **Усиление:** Запретить **любую** конкатенацию/интерполяцию строк в SQL операторах, даже если данные не из конфига
- **Причина:** В DAG файлах SQL должен быть только параметризованным

**2.2. Проверка всех SQL-подобных операторов**
- **Текущее правило:** Проверяет основные операторы
- **Усиление:** Добавить проверку для всех операторов, которые принимают `sql` параметр:
  - `BigQueryOperator`
  - `SqliteOperator`
  - `MSSqlOperator`
  - `OracleOperator`
  - Любые кастомные операторы с `sql` параметром

**2.3. Запрет SQL из переменных окружения без валидации**
- **Текущее правило:** Не проверяет
- **Усиление:** Добавить проверку на SQL, который строится из `Variable.get()` или `os.environ` без валидации

**Рекомендация:** Усилить `airflow-sql-injection.yml` с более строгими паттернами.

---

### 3. **BashOperator/SSHOperator - КРИТИЧНО**

#### Текущее состояние
- ✅ Есть правила для Jinja-шаблонов из `dag_run.conf`, `params`, XCom

#### Что нужно усилить:

**3.1. Запрет любых Jinja-шаблонов в bash_command**
- **Текущее правило:** Проверяет только `dag_run.conf`, `params`, XCom
- **Усиление:** Запретить **любые** Jinja-шаблоны в `bash_command`, кроме предопределенного whitelist (например, `{{ ds }}`, `{{ ts }}`, `{{ dag }}`)
- **Причина:** Даже безопасные на первый взгляд шаблоны могут быть опасны

**3.2. Проверка BashOperator с переменными окружения**
- **Текущее правило:** Не проверяет
- **Усиление:** Запретить использование `os.environ` или `Variable.get()` в командах BashOperator без валидации

**3.3. Запрет множественных подстановок**
- **Текущее правило:** Проверяет отдельные случаи
- **Усиление:** Запретить комбинации нескольких источников данных в одной команде

**Рекомендация:** Усилить `airflow-bash-unsafe.yml` с whitelist подходом.

---

### 4. **Секреты - КРИТИЧНО**

#### Текущее состояние
- ✅ Есть правила для хардкоженных паролей, API ключей
- ✅ Есть правила для Connection с паролями

#### Что нужно усилить:

**4.1. Усилить правила p/secrets для DAG**
- **Текущее правило:** Стандартные правила Semgrep могут быть недостаточно строгими
- **Усиление:** 
  - Сделать все срабатывания `p/secrets` в `dags/` как **ERROR** (блокер)
  - Добавить проверку на короткие токены (могут быть false positive, но лучше перестраховаться)
  - Проверять не только переменные, но и строковые литералы в вызовах функций

**4.2. Запрет секретов в комментариях**
- **Текущее правило:** Не проверяет
- **Усиление:** Добавить проверку на секреты в комментариях (regex для токенов, ключей)

**4.3. Проверка Variable.get() с хардкоженными значениями**
- **Текущее правило:** Не проверяет
- **Усиление:** Запретить `Variable.set()` или `Variable.get()` с хардкоженными секретами в DAG коде

**Рекомендация:** Создать `airflow-secrets-strict.yml` с усиленными правилами.

---

### 5. **Kubernetes/Docker операторы - ВЫСОКИЙ ПРИОРИТЕТ**

#### Текущее состояние
- ✅ Есть правила для динамических `image`, `env_vars`, `volumes`

#### Что нужно усилить:

**5.1. Whitelist для образов**
- **Текущее правило:** Запрещает любые динамические образы
- **Усиление:** Разрешить только образы из предопределенного whitelist (например, из внутреннего registry)
- **Причина:** Иногда нужны динамические образы, но они должны быть из доверенного источника

**5.2. Запрет securityContext из конфига**
- **Текущее правило:** Не проверяет
- **Усиление:** Запретить `securityContext`, `serviceAccountName` из `dag_run.conf`
- **Причина:** Это может привести к эскалации привилегий

**5.3. Проверка volumeMounts**
- **Текущее правило:** Проверяет только `volumes`
- **Усиление:** Проверить также `volume_mounts` и пути монтирования

**Рекомендация:** Расширить `airflow-k8s-operator.yml`.

---

### 6. **XCom с pickle - СРЕДНИЙ ПРИОРИТЕТ**

#### Текущее состояние
- ✅ Есть предупреждение о `enable_xcom_pickling`

#### Что нужно усилить:

**6.1. Сделать ERROR вместо WARNING**
- **Текущее правило:** WARNING
- **Усиление:** ERROR для DAG файлов
- **Причина:** Pickle в XCom - это серьезная уязвимость

**6.2. Проверка кастомных XCom backends**
- **Текущее правило:** Проверяет только стандартные настройки
- **Усиление:** Проверить использование кастомных XCom backends, которые используют pickle

**Рекомендация:** Изменить severity в `airflow-xcom-pickle.yml` на ERROR.

## 🟡 ПРАВИЛА, КОТОРЫЕ НУЖНО ОСЛАБИТЬ

### 1. **HTTP запросы (requests, urllib3) - ОСЛАБИТЬ**

#### Проблема
- Стандартные правила `p/security-audit` могут предупреждать о `requests` без проверки SSL
- В DAG файлах это часто нормальная практика

#### Рекомендация:
- **Исключить** или понизить severity для:
  - `requests.get/post/put/delete` без `verify=True` (может быть нормально для внутренних сервисов)
  - `urllib3` warnings (часто используются в провайдерах Airflow)

**Исключение:**
- Оставить строгие правила для `requests` с данными из `dag_run.conf` без валидации URL

---

### 2. **Работа с файлами - ОСЛАБИТЬ**

#### Проблема
- Стандартные правила могут предупреждать о любом чтении/записи файлов
- В DAG файлах это нормальная практика (логирование, выгрузки, обработка данных)

#### Рекомендация:
- **Исключить** общие правила о работе с файлами из `p/security-audit`
- **Оставить** только проверки на:
  - Пути к файлам из `dag_run.conf`/`params` без валидации (path traversal)
  - Запись в системные директории (`/etc`, `/usr`, `/bin`)

---

### 3. **Generic Python lint правила - ОСЛАБИТЬ**

#### Проблема
- `p/python` содержит много правил для code quality (неиспользуемые переменные, большие функции, etc.)
- Это лучше оставить линтерам (flake8, ruff, pylint)

#### Рекомендация:
- **Исключить** из Semgrep:
  - Неиспользуемые переменные
  - Слишком большие функции
  - Слишком длинные строки
  - Сложность кода
- **Оставить** только security-релевантные правила

---

### 4. **Использование внешних CLI - ОСЛАБИТЬ**

#### Проблема
- DAG файлы часто используют внешние CLI (`gsutil`, `aws`, `gcloud`, `psql`, `kubectl`)
- Стандартные правила могут предупреждать об этом

#### Рекомендация:
- **Разрешить** использование внешних CLI через `subprocess` с фиксированными командами
- **Запретить** только если команда строится из `dag_run.conf`/`params`/XCom

---

### 5. **Импорты и зависимости - ОСЛАБИТЬ**

#### Проблема
- Правила могут предупреждать о небезопасных библиотеках
- В DAG файлах часто используются специфичные библиотеки для работы с данными

#### Рекомендация:
- **Ослабить** предупреждения о зависимостях (это лучше проверять в `requirements.txt` отдельно)
- **Оставить** только проверки на явно опасные библиотеки (например, старые версии с известными уязвимостями)

## 📋 РЕКОМЕНДАЦИИ ПО КОНФИГУРАЦИИ

### Обновленный .semgrep.yml

```yaml
rules:
  # Стандартные наборы правил (с исключениями)
  - id: p/security-audit
    exclude:
      - rule: python.requests.best-practice.use-timeout
      - rule: python.lang.security.audit.path-traversal
      # Исключаем общие правила о файлах, но оставляем path traversal
  - id: p/secrets
    # Оставляем как есть - секреты критичны
  # НЕ включаем p/python - слишком много lint правил
  
  # Кастомные правила для Airflow
  - semgrep-rules/airflow/
  
  # Усиленные правила
  - semgrep-rules/airflow-strict/

# Включаем только DAG файлы
include:
  - "dags/**/*.py"

# Исключаем служебные файлы
exclude:
  - "**/__pycache__"
  - "**/.venv"
  - "**/venv"
  - "**/tests/**"  # Если есть тесты
```

## 📊 СРАВНИТЕЛЬНАЯ ТАБЛИЦА

| Правило | Текущий уровень | Рекомендуемый уровень | Причина |
|---------|----------------|----------------------|---------|
| eval/exec в python_callable | ERROR | ERROR (везде) | Критично |
| SQL конкатенация | ERROR | ERROR (строже) | Критично |
| Секреты в коде | ERROR/WARNING | ERROR (всегда) | Критично |
| BashOperator с Jinja | ERROR | ERROR (whitelist) | Критично |
| requests без verify | WARNING | INFO/исключить | Норма для DAG |
| Работа с файлами | WARNING | Исключить (кроме path traversal) | Норма для DAG |
| Неиспользуемые переменные | INFO | Исключить | Линтер, не security |
| XCom pickle | WARNING | ERROR | Серьезная уязвимость |
| K8s динамический image | ERROR | ERROR (whitelist) | Нужен баланс |

## 📝 ЗАМЕТКИ

- **Баланс между безопасностью и практичностью:** Некоторые правила могут быть слишком строгими и блокировать легитимное использование. Нужно найти баланс.

- **Whitelist vs Blacklist:** Для некоторых случаев (BashOperator, K8s образы) лучше использовать whitelist подход - разрешать только предопределенные безопасные значения.

- **Контекст важен:** Некоторые правила должны учитывать контекст. Например, `subprocess` с фиксированной командой - это нормально, но с данными из конфига - опасно.

- **Интеграция с линтерами:** Semgrep должен фокусироваться на security, а code quality оставить линтерам (flake8, ruff, pylint).
